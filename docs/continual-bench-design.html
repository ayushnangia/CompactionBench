1. Motivation and research question

Modern agent harnesses (Claude Code, Codex CLI, etc.) advertise very large context windows, but they also quietly compact their own history when those windows fill up. Compaction is not a benign summarisation: it can silently drop the exact fact, the latest correction, or the specific binding that an answer depends on.

Core question. If a long benchmark context is injected into an agentic coding harness over many chat turns, does the harness still preserve the right facts when compaction is off vs auto?

Why this framing

  • System-level, not model-level. We evaluate the whole harness (model + scheduler + compaction rule + tool policy), not just the raw LM. That matches how real agents are actually used.
  • Operational, not theoretical. Tasks are driven through the live CLI as subprocesses. The answer the CLI emits is the answer we grade — no hidden retrieval, no API-only shortcut.
  • Honest failure mode for tools. Any tool call at all flips contaminated_by_tools=True and removes that run from the clean metric. The benchmark refuses to credit answers the model could have obtained by reading files, searching, or browsing.

Two factual conditions

ConditionMeaningHow it’s set
off Harness should not compact. Any compaction event is a finding. Claude: DISABLE_AUTOCOMPACT=1. Codex: model_auto_compact_token_limit=2 000 000 000.
auto Harness compacts as it sees fit. We log every event. Claude: default. Codex: explicit threshold (typically 150 000) rather than model default.
Why we pin Codex’s auto-compact threshold. Codex documents model_auto_compact_token_limit but says that when unset it “uses model defaults.” Those defaults are not documented as a number. For benchmark reproducibility we refuse to rely on hidden defaults; every serious sweep pins an explicit threshold.

Why the contexts must be huge

  • Claude Code Sonnet-family models in this env report ~200k context.
  • Codex local metadata reports 272k for gpt-5.4, gpt-5.4-mini, gpt-5.3-codex, and 128k for gpt-5.3-codex-spark.
  • Therefore the main evaluation target is 1M+ context — not 100k — because the whole point is to force harness compaction to become load-bearing.

2. End-to-end pipeline

The flow is deliberately simple. Every stage is a sub-command of cbench (the Typer CLI in compactionbench/cli.py). 

    upstream dataset (HF / JSONL)
              │
              ▼
      ┌────────────────────┐
      │  cbench prepare    │   validates + writes one JSONL row per task
      │  (loaders.py)      │   schema: TaskRow  (Pydantic, extra="forbid")
      └────────────────────┘
              │
              ▼
      ┌────────────────────┐
      │  cbench run …      │   chunks context, drives claude/codex CLI
      │  (run.py)          │   one subprocess per turn, same session-id
      └────────────────────┘
              │
              ▼
      artifacts/runs_direct/<harness>/<model>/<condition>/<task>.json
              │
              ▼
      ┌────────────────────┐
      │  cbench score      │   deterministic scorers per-row
      │  (score.py)        │   rows.csv + summary.{csv,json}
      └────────────────────┘
              │
              ▼
      ┌────────────────────┐
      │  cbench judge      │   optional LLM-as-judge pass
      │  (judge.py)        │   only for borderline deterministic failures
      └────────────────────┘
              │
              ▼
      ┌────────────────────┐
      │  cbench report     │   pretty-prints summary.json
      └────────────────────┘

What the run artifact actually contains

  • Task identity and benchmark metadata
  • Harness, model, condition
  • Chunking stats (chunk_tokens, chunk_count, context_tokens_est)
  • Compact per-turn traces (role, kind, char/token count, 400-char preview)
  • All tool events (any tool event means the run is contaminated)
  • All compaction events (before/after tokens when the harness reports them)
  • Raw final answer text + the parsed { "answer": "..." } JSON
  • parse_ok, correct, contaminated_by_tools, error, duration_s
Lean by design. Run artifacts do not duplicate the full context — only a 400-char preview per turn. The task JSONL is the canonical source for the long text, artifacts are the operational log.

4. Loaders — upstream benchmarks

compactionbench/loaders.py

Each supported benchmark has a from-file loader (local JSONL) and a from-HF loader (parquet over Hugging Face’s datasets API). Both emit the same TaskRow type and both validate every row before writing.

RULER

  • Clean synthetic retrieval-style long-context stress tests.
  • Task-to-question/scorer map hard-coded in RULER_TASK_CONFIG.
  • Covered: NIAH single/multikey/multivalue/multiquery, variable tracking, common/frequent words, doc-grounded QA.
  • Default min_length=1_000_000 — we only keep the 1M variants.

BABILong

  • Canonical dataset: RMT-team/babilong (not RMT-team/babilong-1k-samples, which has no 1M split).
  • Pilot range: qa1–qa5.
  • Extended range: qa6–qa20 — adds coreference, time reasoning, deduction/induction, positional reasoning, path finding, motivations.
  • qa8 is a special case: answers are comma-separated sets like apple,football, so it uses the set-aware csv_set_ci scorer instead of exact string match.
  • Main Codex sweep starts at 128k, not 4k, because compaction only becomes load-bearing above ~128k.

OOLONG-synth

  • Clean verifiable aggregation tasks with explicit context-length buckets.
  • Task groups used: counting, user, timeline.
  • Scorer inference is structural — numeric, date, month-year, comparison, and CSV variants all have dedicated normalisers in score.py.

OOLONG-real

  • Real multi-episode transcripts — currently the D&D (dnd) config.
  • Prefers episode-count buckets (3ep, 6ep, 10ep, 16ep) over pretending tokens are exactly a power of two.
  • Approximate scales: 3ep ≈ 129k, 6ep ≈ 298k, 10ep ≈ 458k, 16ep ≈ 773k.
  • Questions go through _parse_oolong_real_gold which picks the right scorer (oolong_text_ci, oolong_comparison_ci, date_ci, month_year_ci, numeric_075, csv_overlap_ci).
Resilient HF paging. The loaders use a _read_hf_rows_page_resilient helper that handles IncompleteRead and retries with smaller pages, so a transient Hugging Face hiccup doesn’t kill a preparation run mid-sweep.

5. Context chunking

compactionbench/chunking.py

Chunking is intentionally minimal. The design goal is fidelity: the emitted chunks, concatenated, should be byte-identical to the original context wherever possible.

  • CHARS_PER_TOKEN = 4 — the universal rough conversion.
  • MAX_CHUNK_OVERFLOW = 1.2 — a paragraph up to 20% over target size is kept intact rather than split.
  • Paragraph boundaries are matched by re.compile(r"\n\s*\n") and preserved verbatim in the emitted chunks.
  • Only paragraphs that exceed the overflow budget are raw-sliced by character (_split_raw) — no sentence-tokenisation, no normalisation, no whitespace collapsing.
Why fidelity matters. Earlier versions of this code normalised whitespace when merging paragraphs and split long paragraphs on sentence boundaries. That accidentally edited the task during preparation. Current chunking is lossless-by-default.

6. Harness runners

compactionbench/run.py

Each runner is a Python class that drives the real CLI binary as a subprocess. There is no API fast-path; the point of the benchmark is to measure the harness, not just the model.

Shared structure

  1. chunk_text(task.context, chunk_tokens) → list of chunks.
  2. Loop over chunks, for each one:
    • Build the chunk prompt (build_chunk_prompt):
      “Context chunk i/N. Store this for later. Do not answer the final question yet. Do not use tools. Do not browse. Reply only with: OK” + chunk text.
    • Start a subprocess; on turn 1 pass --session-id (Claude) or no resume flag (Codex), otherwise resume the same session.
    • Parse the streamed JSONL output for assistant text, tool events, and compaction events.
    • Record two TurnTraces (user + assistant) with previews capped at 160 chars (preview()).
  3. Final turn: build_final_prompt(question) asks for exactly {"answer": "..."}.
  4. Parse the last balanced JSON object, score it, write the artifact.

ClaudeCodeRunner specifics

claude -p <prompt> --bare --model <model>
  --effort <low|…> --output-format stream-json --verbose
  --tools "" --permission-mode default
  --disable-slash-commands --strict-mcp-config
  [--settings <json>]   # for apiKeyHelper bare-mode auth
  --session-id | --resume
  • Runs --bare for clean isolation. OAuth/keychain auth is not read by bare mode; strict runs need ANTHROPIC_API_KEY or --settings with an apiKeyHelper.
  • Tool allowlist is empty string — the run cannot use tools at all.
  • Compaction events are detected from type=system, subtype=compact_boundary with compact_metadata.pre_tokens / post_tokens.
  • Server-side web_search_requests / web_fetch_requests counts in the final type=result event are also recorded as tool events.

CodexRunner specifics

codex -m <model> -a never -s read-only -C <tmpdir>
  -c model_reasoning_effort=<…>  -c model_verbosity=<…>
  -c web_search=disabled
  -c model_auto_compact_token_limit=<off_limit | auto_limit>
  exec [--skip-git-repo-check] [resume <sid>] --json <prompt>
  • Sandbox is read-only, approval policy is never, web search is disabled — tools cannot contaminate the run.
  • Compaction signals come from context_compacted, compacted, or event_msg with payload type context_compacted.
  • If the streamed JSONL didn’t include compaction events (some older codex builds only record them in the session log), the runner falls back to scraping ~/.codex/sessions/**/*<session_id>.jsonl via _load_codex_session_compaction_events.
Contamination is strict. The definition is simply len(tool_events) > 0. A single unexpected tool invocation removes the run from the clean denominator. This is intentional — the benchmark refuses to grade answers the harness could have looked up.

7. Scoring

compactionbench/score.py  ·  compactionbench/judge.py

Deterministic pass (cbench score)

Every scorer returns a float in [0, 1]. A row is marked correct iff score_value ≥ 1.0. Gold aliases are handled with max(func(answer, candidate) for candidate in (gold, *aliases)).

ScorerBehaviourTypical use
exactcase-sensitive strip-compareRULER single keys (when exact case matters)
exact_cicase-insensitiveBABILong qa1–qa7, RULER niah_single
substring_cigold must appear inside answer (case-insensitive)RULER multivalue/multiquery, vt, cwe, fwe, qa_1/2
multiple_choicefinds first \b[ABCD]\b in answerMCQ-style upstreams
csv_set_cisorted set of lower-cased tokens == gold setBABILong qa8 (e.g. apple,football)
numeric_075partial credit: 0.75 ** |pred − gold|OOLONG counting (exact gets 1.0, off-by-1 gets 0.75…)
csv_overlap_ci|gold ∩ pred| / |gold|OOLONG set-overlap questions
oolong_text_cinormalises **, \boxed{…}, prefixes like label:, bracketsOOLONG text answers
oolong_comparison_cicanonicalises to more common / less common / same frequencyOOLONG comparison
date_cicanonicalises multiple date formats to ISO YYYY-MM-DDOOLONG timeline dates
month_year_cicanonicalises “March 2025” / “Mar 2025” to a single formOOLONG month-year questions

Aggregation

_aggregate groups by (harness, model, condition) and also by (harness, model, condition, benchmark), and reports:

  • n_total, n_clean (non-contaminated), correct_clean, correct_all
  • accuracy (on clean), accuracy_all
  • avg_score (mean over partial-credit scorers)
  • parse_ok_rate, contaminated_rate, errors, compaction_events, avg_duration_s

LLM-as-judge pass (cbench judge)

  • Model: qwen/qwq-32b via OpenRouter (temperature 0, max 300 tokens).
  • Runs only on rows where deterministic scoring failed and parse_ok is true, the run is not contaminated, and the answer is non-empty. Correct rows and contaminated rows are never re-judged.
  • Prompt is strict: "Do not award credit for clearly different facts. Ignore only superficial formatting differences." Returns { "equivalent": bool, "reason": str }.
  • Final metric: deterministic_correct OR judge_equivalent.
  • Parallelised with a ThreadPoolExecutor; default 4 workers.
Why keep both. Deterministic accuracy is the honest number for a paper. Judge-adjusted accuracy tells us whether failures are “close but wrong in formatting” vs actually wrong — which changes the interpretation of compaction behaviour.

Chunk size scales with context. Short contexts use small chunks (more turns, more compaction pressure observable); long contexts use bigger chunks so the absolute turn count stays manageable within the timeout. This is per-length, explicitly listed in the spec.

9. Results so far

9.1 BABILong qa1–qa10 — the foundational sweep

artifacts/batches/babilong_codex_auto_high_models_parallel/20260422-123112

What BABILong is

A long-context benchmark built on the classic bAbI reasoning tasks, but with the supporting facts hidden inside a massive distractor context (filler text from PG-19 books). The model has to find the relevant needles in a very long haystack.

qa1–qa10 — the “exact fact” family

TaskNameWhat it probes
qa1single supporting fact“Where is Mary?” — one-hop retrieval
qa2two supporting factsChain two facts together
qa3three supporting factsThree-hop retrieval
qa4two-arg relations“What is east of the bedroom?”
qa5three-arg relations“Who gave X to Y?”
qa6yes/no questionsBinary fact check
qa7counting“How many objects is Mary carrying?”
qa8lists / setsAnswers like apple,football — set-aware scoring
qa9simple negationHandling “not” and absence
qa10indefinite knowledge“maybe” / uncertain answers

Sweep setup

3 Codex models (gpt-5.4, gpt-5.4-mini, gpt-5.3-codex) × 4 lengths (128k, 256k, 512k, 1M) × auto compaction with threshold 150 000 = 120 runs.

120total runs 8.3%det. accuracy 39.2%judge-adj. accuracy 90/120runs with compaction 3.62avg compactions / run

Main finding

  • Deterministic accuracy was only 8.3% but judge-adjusted was 39.2% — the model often produced semantically close but not exact answers.
  • Compaction started at 256k and was heaviest at 1M.
  • Readout: default compaction preserves the gist but loses the exact binding that BABILong grades.

9.2 BABILong qa11–qa20 — the reasoning extension

artifacts/batches/babilong_codex_auto_high_models_qa11_to_20_s3/20260422-095719

What qa11–qa20 add

Higher-level reasoning that goes beyond “retrieve the right fact”.

TaskNameWhat it probes
qa11basic coreferencePronoun resolution across long spans

qa13compound coreferenceNested pronouns / multiple referents
qa14time reasoning“What did X do before Y?”

Sweep setup

Same 3 models × 4 lengths × auto = 360 runs.

360total runs 123resolved (not usage-limited) 43.1%det. acc. on resolved 82.9%judge-adj. acc. on resolved 237usage-limit failures

Main finding

  • 237/360 runs were killed by usage-limit failures — an honest blemish in the data, not hidden.
  • On the resolved subset: 43.1% deterministic, 82.9% judge-adjusted.
  • Stronger: coreference (qa13, qa11) and deduction (qa15) — the reasoning is local once the right facts are found.
  • Weaker: path finding (qa19), positional (qa17), motivations (qa20), time (qa14) — these need structured multi-step reasoning that compaction tends to disrupt.
Honest denominator. The analyzer tracks a resolved subset alongside the raw total precisely because a usage-limited run is a failure of the infrastructure, not of the model. The resolved-only numbers are the fair readout.

9.3 OOLONG-synth — the aggregation sweep

artifacts/batches/oolong_synth_codex_auto_high_models/20260423-173654

What OOLONG is

A different kind of long-context test. Instead of “find a needle,” tasks require aggregating many local decisions across the whole context. You cannot answer by retrieving one passage — you have to integrate evidence spread throughout.

Three task groups used

GroupWhat it probes
counting“How many times did X happen?” — count events across the context
userAttribute actions / preferences to specific users across a long log
timelineReconstruct order-of-events from scattered mentions

Sweep setup

Same 3 models × 4 lengths × auto = 108 runs, 107 resolved (operationally clean, unlike qa11–qa20).

108total runs 107resolved 46.3%det. accuracy 81/108runs with compaction 2.55avg compactions / run

Main finding

  • Deterministic accuracy 46.3% — much higher than BABILong.
  • By task group: counting 58.3% (easiest), timeline 44.4%, user 37.1% (hardest — aggregation tied to a specific entity).
  • Compaction again starts at 256k but the average number of compaction events per run is lower (2.55 vs BABILong’s 3.62).

9.4 Cross-benchmark readout

SweepWhat it probesUnder compaction…
BABILong qa1–qa10 Exact symbolic memory Brittle — gist survives, exact binding is lost
BABILong qa11–qa20 Structured reasoning over retrieved facts Mixed — coreference/deduction OK; path, position, motivation weak
OOLONG-synth Aggregation over many local decisions More survivable — summaries preserve counts and trends
Why running all three matters. The asymmetry — exact-state tasks fail, aggregation tasks partially survive — is exactly what motivates the tiny-notebook sprint (§11). Default compaction seems to keep the kind of memory that helps aggregation but hurts exact-state tasks. A structured working note could plausibly rescue the latter without costing the former. Comparison artifacts live under artifacts/analysis/oolong_vs_babilong/.

10.3 Why this is the interesting state

This is the first sweep over real multi-episode transcripts. The previous three sweeps used either synthetic retrieval haystacks (RULER), synthetic reasoning puzzles (BABILong), or synthetic aggregation (OOLONG-synth). OOLONG-real is messier, more realistic narrative, and uses episode-count buckets instead of power-of-two token targets.

Operationally, the episode-count matrix is the right abstraction: episode count is the natural unit of the upstream dataset, and pretending a 6-episode D&D transcript is exactly “298 144 tokens” would be false precision. Token estimates are recorded in metadata for reporting, but the primary bucket is episode count.

11. Exploration sprint — tiny notebook

exploration_sprint.md

The next curiosity-driven sprint is already scoped. The hypothesis is that harness compaction keeps the gist but loses the exact state, and a tiny structured notebook inside the agent loop might rescue exact-memory tasks without helping aggregation tasks as much.

The new condition

  • auto — current default compaction.
  • auto+notebook — every few chunks, the agent writes a tiny fixed-format note: latest known facts, corrections, key entities, dates/times, unresolved conflicts. Not a chain of thought, not a summary — just a working note.

Minimal sprint matrix

AxisValues
BABILong tasksqa1, qa11, qa14
OOLONG taskscounting, timeline
Lengths256k, 1M
Modelsgpt-5.4, gpt-5.4-mini
Duration1 week. Hard-stop 2026-04-30.

Pre-registered expectations

  • Notebook helps BABILong more than OOLONG.
  • Notebook helps exact-memory tasks more than aggregation tasks.
  • Notebook does not help path finding or deep structured reasoning.

What would count as a real surprise

  1. Notebook helps OOLONG a lot but barely helps BABILong → the real issue isn’t exact symbolic loss but something about task decomposition.
  2. Notebook hurts performance → extra notebook tokens cause more compaction, or model trusts bad notes, or external notes interfere with internal reasoning. Opens a different research direction on naive memory aids backfiring.

Decision rule

  • Graduate if notebook clearly helps exact-memory tasks at long lengths, more than aggregation.
  • Shelve if no real difference.
  • Pivot if an interesting unexpected effect shows up instead.

13. Caveats, guardrails, open questions

Explicit scope-cuts (things the repo deliberately does not do)

  • No README.md task fixtures.
  • No docs/chunk_XX.md split files.
  • No distractor padding machinery.
  • No manual compaction variants — only harness-native off / auto.
  • No file-reading benchmark tasks — the context must live in conversation history, never on disk.

Guardrails

  • extra="forbid" on every Pydantic model.
  • ensure_unique_task_ids runs at write time and before every batch run.
  • Claude --bare + --tools "" + --strict-mcp-config.
  • Codex -a never + -s read-only + web_search=disabled.
  • Any tool event → run is excluded from the clean metric.
  • Per-run temp workdir so cached files from one task can’t leak to the next.

Known limitations

  • OAuth-only Claude runs are not the strict benchmark condition. Bare mode does not read keychain/OAuth auth; strict runs require ANTHROPIC_API_KEY or apiKeyHelper-based --settings.
  • Usage-limit failures were significant in the qa11–qa20 extension (237/360). The analyzer now tracks a resolved subset as the honest readout.
  • OOLONG-real prepared set has so far only used the negation subset for stability. The in-progress sweep adds multidoc_rolls and multidoc_spells over 3–16 episodes.
  • No manual compaction variants — we measure the default harness behaviour, not an intervention. The sprint in §11 is the first proposed intervention.

Open questions worth naming

  1. Does auto+notebook specifically rescue exact-memory tasks, as predicted, or does it backfire by inflating context and triggering more compaction?
  2. Do OOLONG-real multi-episode transcripts compact earlier than synthetic contexts of similar token count, because they lack the regular structure a summariser can exploit?
  3. What is the correct denominator for the main metric in the presence of usage-limit errors — total, resolved, or resolved-and-clean? (Current default: resolved-and-clean.)
  4. Is judge-adjusted accuracy “free lunch” signal, or is a qwq-32b judge too permissive on BABILong-style exact answers?
