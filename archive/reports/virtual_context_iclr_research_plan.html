Proposed paper title

Virtual Context Memory: System-Managed Evidence Paging for Long-Context Agents

Alternative shorter title: Who Should Manage Context? System vs. Model Memory Management in Long-Context Agents

Core thesis

Long-context agents should not rely on the model to remember or search everything. Like an operating system, the agent runtime should manage a memory hierarchy: original sources live outside the model, a memory kernel retrieves a resident evidence set, and the model answers from that evidence.

What this is not

Not “grep always beats full context.”

Not “we solved infinite context.”

Not “RAG with a new name.”

What this is

A controlled study of who manages memory: the model, tools, or the system.

A first implementation of transparent resident-set retrieval.

Research question hierarchy

RQQuestionCurrent evidenceNeeded for ICLR
RQ1Does system-managed memory beat model-managed search?Virtual context beats grep overall in 1500-run BABILong/OOLONG experiment, with strongest effect on BABILong.Repeat on more models and no baseline re-runs; add confidence intervals and ablations.
RQ2Which task types benefit?BABILong exact event/state tasks benefit. OOLONG aggregation does not.Formal task taxonomy: lookup, state tracking, spatial, transfer, counting, first/last, frequency.
RQ3Is manual paging worse than transparent paging?Manual paged_context underperforms grep; transparent virtual context beats both overall.Show model-visible paging imposes cognitive/tool burden via tool counts, latency, and error analysis.
RQ4Does resident-set budget matter?8k/24k/48k are similar, but budgets were not strictly enforced.Fix hard budgets and sweep 2k/4k/8k/16k/32k with exact token caps.
RQ5Can page-fault retries close remaining failures?Not implemented yet.Add verifier: unsupported answer → retrieve more evidence → retry.
RQ6Can structured memory operators solve aggregation?OOLONG remains hard for all retrieval methods.Add roll/spell table extractors and deterministic count/sort/filter operators.

Method taxonomy: the memory ladder

Level 0
Full contextEverything in prompt. No explicit memory system.
Level 1
File searchModel searches one monolithic file with grep/tools.
Level 2
Manual pagingModel sees page table and decides which pages to load.
Level 3
Virtual contextSystem retrieves resident evidence before model call.
Level 4
Faulted contextVerifier detects missing evidence and triggers retrieval retry.
Level 5
Structured memoryTyped pages + table/count operators for aggregation.

Why reviewers might reject it

Weakness 1: “This is just RAG.”

Answer: position the contribution as memory-management responsibility and controlled comparisons across full context, grep, manual paging, and transparent memory.

Weakness 2: “Small effect / possible fluke.”

Answer: add repeated runs, models, paired bootstrap CIs, and larger fixed panels. Report where effect does and does not hold.

Weakness 3: “Task-specific heuristics.”

Answer: own it as typed memory pages; then ablate generic retrieval vs typed extractors. For ICLR, show both general and typed versions.

Weakness 4: “No real page faults.”

Answer: implement Level 4: verifier-triggered retrieval retry. Current is Level 3 transparent resident-set retrieval.

ICLR-grade experiment plan

  1. Freeze panels and reuse baselines. No more baseline reruns unless task/model/protocol changes.
  2. Run new arms only: hard-budget virtual context, faulted virtual context, structured virtual context.
  3. Add models: at least two closed models and one open model if possible.
  4. Add stochastic repeats: pass@2 or 3 independent completions on a subset to estimate variance.
  5. Do paired stats: McNemar/sign tests, bootstrap CIs, effect sizes, by-dataset and by-task-type.
  6. Do ablations: no task hint, generic retrieval only, typed extractor only, no neighbor pages, budget sweep.
  7. Do failure taxonomy: wrong page, missing page, stale state, relation inversion, aggregation failure, formatting-only miss.
  8. Release artifacts: task panels, run records, selected evidence packets, analysis notebooks/scripts.

Proposed paper outline

1. Introduction
   - Long-context agents need memory management, not just bigger prompts.
   - Analogy: OS virtual memory.

2. Problem setup
   - Source memory, question, model context budget.
   - Memory-management responsibility axis.

3. Methods
   - Full context, file search, manual paging, virtual context.
   - Virtual Context Memory implementation.

4. Benchmarks
   - BABILong, OOLONG-real, SWE-chat, LongMemEval rendered.
   - Explain scoring and caveats.

5. Experiments
   - Fixed panels, paired comparisons, budgets, ablations.

6. Results
   - System-managed memory helps exact retrieval.
   - Manual paging is worse than grep.
   - Aggregation requires structured memory.

7. Analysis
   - Evidence packet audits.
   - Failure taxonomy.
   - Statistical significance.

8. Related work
   - RAG, tool use, memory agents, long context.

9. Limitations
   - Task-specific extractors, no full page faults yet, model coverage.

10. Conclusion
   - Memory should be a runtime/system layer.

Claim discipline

Safe claim: “System-managed virtual context shows a mechanism-consistent advantage over model-managed search on exact memory retrieval, while aggregation still requires structured operators.”

Unsafe claim: “Virtual context beats grep” without task/dataset caveats.
