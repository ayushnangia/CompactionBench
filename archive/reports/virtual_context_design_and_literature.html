Virtual Context Memory

How the memory kernel, hidden page table, retrieval rules, and evidence packet are built — and how this relates to existing literature.

First: are we sure this is the best formulation?

Best current formulation: call it Virtual Context Memory, but be precise: the implementation is currently transparent prefetch / resident-set selection, not a complete OS with real page faults yet.

So the honest claim is:

We move retrieval and page selection out of the model and into a system memory kernel. The model receives a resident evidence packet instead of manually searching pages.

Good name for the idea

Virtual Context Memory

Good because it captures the OS analogy and the goal: context larger than the prompt, mediated by a memory system.

More precise method name

Transparent Resident-Set Retrieval

Good for papers because it avoids overclaiming full OS paging before page faults/eviction are implemented.

What exactly is the “memory kernel”?

The memory kernel is not a separate daemon yet. It is the harness code that runs before the model call.

Current algorithm in plain pseudocode

def answer_with_virtual_context(source, question):
    pages = split_source_into_pages(source)
    page_table = build_hidden_index(pages)

    if benchmark == "BABILong":
        evidence = extract_babi_event_trace(pages, question)
    elif benchmark == "OOLONG":
        evidence = retrieve_roll_spell_windows(pages, question)
    else:
        evidence = score_pages_by_question_terms(pages, question)

    packet = fit_evidence_to_budget(evidence)
    prompt = render_prompt(question, packet)
    answer = model(prompt, tools_disabled=True)
    record_audit_trail(packet)
    return answer

Is it the best formulation?

Yes, for the research story

“Virtual context” is a strong framing because it explains why giant prompts and manual grep are not the final design. Agents need a memory subsystem, not just a bigger prompt.

It also gives us clean experimental axes: model-managed search vs system-managed memory.

But tighten the claim

Current implementation is static transparent prefetch. It is not yet full OS paging because there is no page-fault loop, eviction policy, hard budget enforcement, or learned retrieval index.

So avoid saying “we built infinite context.” Say “we built a first transparent virtual-context memory arm.”

What I would change next

  1. Hard enforce resident-set budgets. The 8k/24k/48k labels were not hard enough in the latest run.
  2. Add a verifier-driven page-fault loop. If answer is unsupported, retrieve more pages and retry.
  3. Add typed pages. BABI event pages, OOLONG roll table pages, spell table pages, conversation-turn pages.
  4. Add structured operators for OOLONG. Count rolls, compute percentages, first/last spell by episode/character.
  5. Use hybrid retrieval. Lexical search + entity index + embeddings + task-specific extractors.
  6. Do not re-run baselines. Reuse fixed-panel baselines and run only new arms.

Final recommendation

Keep the formulation, but phrase it carefully:

Virtual Context Memory is a system-managed memory layer for long-context agents. It keeps source text outside the model, pages and indexes it, retrieves a resident evidence packet, and lets the model answer without manual search. The current implementation is transparent prefetch; the next version adds page-fault retries and structured operators.
