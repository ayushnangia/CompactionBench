Recursive Language Models

Notes on arXiv:2512.24601 and what it means for our virtual-context work.

paper: 2512.24601Alex L. Zhang, Tim Kraska, Omar KhattabMIT CSAILRLM ≠ relevance model

Correction

I initially interpreted “RLM” as a retrieval relevance language model / RM3. That was wrong for this paper.

Here, RLM = Recursive Language Model: an inference-time scaffold where the prompt is stored as an external object in a REPL, and the model writes code to inspect, transform, and recursively call LMs/RLMs on slices of the prompt.

Paper in one paragraph

The paper argues that arbitrarily long prompts should not be directly stuffed into the neural model context. Instead, the prompt should live in an external environment. The root model receives metadata and a symbolic handle to the prompt, writes code in a REPL to inspect/decompose it, stores intermediate results in variables, and can call sub-LMs or sub-RLMs over programmatically chosen chunks. This can do dense semantic work over inputs far beyond the base context window.

Core algorithm

state = InitREPL(prompt=P)
state = AddFunction(state, sub_RLM_M)
hist = [Metadata(state)]

while True:
    code = LLM_M(hist)
    state, stdout = REPL(state, code)
    hist = hist + code + Metadata(stdout)   # stdout is summarized/truncated
    if state[Final] is set:
        return state[Final]

Key: the prompt and intermediate values live in the REPL state, not in the model history.

The three design choices that matter

Design choiceMeaningWhy it matters
Symbolic handle to promptThe prompt is stored as context in the environment.The root model does not need the entire prompt in context.
Intermediate state outside model contextLarge buffers, extracted tables, chunk results live in variables.Avoids compaction and context pollution.
Programmatic recursionCode can call llm_query or rlm_query inside loops.Allows O(n) or O(n²) semantic work over prompt chunks.

How this differs from our current virtual context

Our virtual contextRLM paper
System retrieves evidence before the model call.Model writes code to inspect/decompose the source during inference.
Model sees an evidence packet only.Model sees a REPL interface and can manipulate a context variable.
Currently one-shot: no retry/page fault.Iterative loop until Final is set.
Typed extractors help BABILong.Sub-LM calls help semantic/dense tasks like OOLONG.
More system-managed / OS-kernel-like.More programmatic / recursive-agent-like.

Why this matters for us

For BABILong

Our virtual context already works because event extraction is easy. RLM may not add much unless we use it to derive state with code.

For OOLONG

RLM is directly relevant: OOLONG needs semantic labeling over many lines and aggregation. The paper says recursive sub-calls help exactly here.

Correct RLM-based experiment to try

Do not use RM3/query expansion. That was the wrong interpretation.

Correct new arms:

rlm_repl_depth0     # context in REPL/file variable; model writes code; no sub-LM calls
rlm_repl_depth1     # same, but code can call llm_query(chunk_prompt) on chunks
rlm_virtual_hybrid  # RLM REPL plus our typed virtual-memory APIs

Practical implementation sketch

Workspace:
  context.txt                # full source, outside prompt
  rlm_env.py                 # helper functions
  task.json                  # question, metadata

Prompt:
  You are in an RLM-style REPL.
  The full context is available at ./context.txt.
  Write Python to inspect/decompose it.
  Store intermediate results in variables/files.
  Return final JSON answer.

Depth 0:
  model writes Python, regex, parsing, counting

Depth 1:
  provide llm_query(prompt) helper
  model can call sub-LLM on chunks and aggregate results

What to run first

  1. Stop using RLM/RM3 terminology for the query-expansion arm.
  2. Implement rlm_repl_depth0 first. This is cheaper and close to paper's depth=0 ablation.
  3. Run only new arms on fixed BABILong/OOLONG; reuse baselines.
  4. Then implement depth=1 with a controlled llm_query helper for OOLONG chunks.
  5. Compare against our virtual context: system-managed prefetch vs model-programmed recursion.

Paper claims relevant to our writing

  • Compaction assumes early details can be safely forgotten; this fails on dense tasks.
  • Effective context window depends on task complexity.
  • Needle tasks are O(1); OOLONG is linear; OOLONG-Pairs is quadratic.
  • REPL is necessary for handling long inputs; recursive sub-calls help information-dense tasks.
  • Training models on RLM trajectories can improve downstream RLM behavior.
